## 2. 修复建议需要怎样调整

### 结构化依据仍然需要语义判断

把关键词匹配改成结构化 JSON 只是契约修复，不能自动保证正确。依据至少需要描述：主张的对象和关系、方向、肯否、条件、适用范围、来源、支持与反对证据、判断方式及未决原因。字段填满、模型自报高分、两个模型意见一致，都不等于业务事实已被证明。

同时，不能反过来要求每次归并必须有统一编码或一条明确写出结论的文档。用户需要 Agent 综合元数据、字段关系、少量数据、已有图和松散知识进行推断。程序校验结构、范围、引用与可执行约束；Agent 负责提出业务解释；不足或冲突保留候选。自动接受策略需要独立语义评测，不能只靠替身测试。

### 候选应该可见，但要能解释和裁决

保留只含 accepted 的消费接口；工作台探索视图可以同时显示候选、已接受与冲突，并明确状态、原因、支持及用户操作。不得把“隐藏所有候选”作为解决误发布问题的方式。用户裁决需要有版本、作用范围和撤销能力。

### 去掉分区值哈希必须同时保证正确对账

随机 token 或分区序号只能作为本轮临时引用。若直接把它当跨轮身份，重排、取消和恢复后可能错撤回支持。后续设计采用运行内临时引用和完整规则代际发布；只有已获输出授权的逻辑范围才可具有稳定持久引用。完整边界内成功替换，失败保留旧发布并标明状态。

代际完整还要求来源一致：跨轮分析或重启后，如果不能验证来源版本，就废弃受影响代际的 staging 并重读完整提交范围，不能拼接前后快照。图级复核使用独立的待发布图视图，不能为检查新图而提前发布。

也不应删除所有 hash：已允许输出的事实去重、文件完整性检查，与未允许保存的源键哈希是不同问题。性能是否受 hash 影响还没有剖析证据；当前可确认的是语义误用与留存违规。

### F 台账要复用现有测试，而不是按文件名重写一套

例如现有 `test_pipeline.py` 已覆盖共享别名撤回、预算不足、依赖集更新、增量身份与导出；`test_relative_hierarchy.py` 已覆盖跨列位置、跨表支持、迁移和上下文层级；`test_retention_lifecycle.py` 已有失败路径留存检查。这些是有效工程证据，但尚不能替代逐个 F 场景的独立真值对照。

每个 F 应记录输入生成器或夹具、独立真值、禁用边/禁用归并、预期未决、执行命令、提交、模式 E/D/I、实际结果与缺失子场景。源码中的夹具可以保留，不要求仅为满足文件名再复制 CSV。评估器真值不能进入发现 Agent 的输入。

## 3. 外部报告之外仍必须解决的核心缺口

1. **业务词汇仍受固定类别、关系与属性限制。** `store/policy.py` 和发现模型的枚举适合当前指标演示；平台需要由目标和数据产生项目级语义定义，同时保留严格输出与权限约束。
2. **单次 Agent 工具循环不等于跨阶段迭代。** 现有上下文组装和短生命周期 Agent 可复用，但需要把规则执行中的未知模式送回新任务，并带入已有知识、目标修订和待解决问题。
3. **字段关联到实体关系需要明确转换契约。** 列组、关联谓词、端点映射和实例投影必须贯通。数据库外键、值重合与业务关系不是同一个结论；确认端点与语义后才能形成对应实例边。
4. **身份归并不能由单一编码或 hash 决定。** 已有稳定 UUID、相对层级和来源绑定是基础；还缺少通用候选检索、跨来源语义复核及可撤销的图级归并。
5. **完整构图后还要复核关系。** 同端点多条关系可能合法共存；真正冲突、同义写法、时间或条件不同需要分别处理。全图遍历也不能等同于穷举所有节点对。

因此实施顺序应同时覆盖缺陷与目标：先阻止错误的 accepted 关系/归并和违规留存，建立目标修订及任务状态；随后完成“新模式 → 新 Agent → 修订 → 重算 → 图复核”的最小完整场景，再扩展工作台裁决与独立验收。修完外部报告中的缺陷，不应直接把项目标为目的已实现。
