# 实例验证、工具生命周期与重新运行

本次依据用户转述的真实运行轨迹检查当前源码。未取得客户的原始 trace、草稿和数据库，不能把转述中的时间线、内存量或身份冲突归因当作已复现事实。修复面向可复现的程序行为，不预置指标、维度或层级规则。

## 1. 故障与预算应分层判断

| 配置或现象 | 实际作用及判断边界 |
| --- | --- |
| 顶层 `max_working_bytes` | 实例投影、图谱与索引的本地工作集准入限额；不是 token 或数据库内存，也不是 Python RSS 的精确测量。默认 32 MiB，用户可配置更大值；不能保证设为 1 GiB 就足够。 |
| `limits.timeout_ms` | 单次来源查询的时间限制，不是整个实例验证的 MCP 等待时间。 |
| `model.timeout_seconds` | 模型请求超时，不应连带截断需要执行多次查询的工具。 |
| `max_run_seconds` | 本轮总时间；工具等待、查询执行和模型分发仍需服从剩余时间。 |
| `model.working_context_tokens` | 原生 Harness 自动压缩的触发目标，不是全部长期记忆，也不是服务商模型容量。 |
| `same_identity_conflicting_label` | 同一类型、完整身份及访问范围下存在不同主名称；不证明必须增加责任中心键，也不证明跨层位复用错误。需要核对列绑定、范围和名称语义。 |

缓存零命中只表示没有复用同一完整投影，不能推出所有历史投影同时留在内存。原执行器已在最后一个消费者完成后释放一次性缓存。仅让 `context_columns` 相同，也不能保证键、标签、别名、筛选和实际投影集合一致。

原生 compactor 会拒绝达到输出上限的摘要，再保留原历史；不能据此认定截断摘要已经替换了有效记忆。反复压缩失败确实会增加调用和检索开销，但与 MCP 不可用、草稿无法方便重读分别处理。`construction_tool_not_allowed` 是工具授权守卫的拒绝码，本身也不能证明 MCP 服务已经死亡。

## 2. 物化与诊断

实例累积原先会对不断增长的整份节点或边反复序列化，并线性查找重复支持。同一节点拥有大量来源支持时，这些操作的总成本接近平方增长。

改为按新增属性、别名和来源支持增量计量，使用定长摘要索引查重。完整值、位置与行路径仍保留在图中，索引另计估算开销。支持数增加时，序列化工作量应随新增贡献近似线性增长。预算依然可以拒绝确实过大的图；不通过删名称、丢上下文或忽略冲突降低验收要求。

内存诊断记录失败阶段、实际配置限额、估计需求、图载荷、投影缓存、查找索引和累积索引。记录明确标注不是 RSS。每次验证的回复也返回生效限额，便于确认新运行是否真的采用了用户保存的配置。

大量数据冲突在工具回复中只展示首批，同时返回总数、按代码计数以及完整验证材料入口。所有诊断仍写入原验证文件，不能因回复缩短而获得发布资格。

## 3. 工具调用与原生上下文

MCP 领域服务使用无状态 HTTP 协议；业务状态仍由持久工作区管理，授权令牌与工具白名单保留。同步实例验证移到工作线程，事件循环继续处理协议请求，写操作仍串行。调用方断开不能启动第二次相同物化，也不能在旧工作尚未结束时关闭其适配器。

工具等待期限与本轮剩余总时间对齐，不再复用模型请求超时。单次 SQL 仍遵守来源限额，重连不能重放部分读结果。不可恢复的图工具传输故障触发程序控制的有界收尾；原生会话搜索、压缩和模型重试同样消耗收尾额度，不能以不断翻历史绕过停止条件。故障不自动删除草稿或降级目标。

### 长工具请求的 HTTP 等待

无状态 HTTP 也可以使用 SSE 响应。此前 `json_response=True` 会等工具执行完才发响应头；即使 MCP SDK 的调用期限足够长，Node fetch 仍可能先达到默认 300 秒的响应头等待上限。约五分钟后出现 `fetch failed` 与这一机制相符，但仅凭该错误不能认定现场 Python 进程死亡、杀软干预或数据库断线。

服务改用 Python MCP 原生 SSE：先发 HTTP 响应头，执行期间由 SSE 库每 15 秒发送注释心跳，完成后返回一份工具结果。原生 Node MCP 客户端解析这些消息，注释心跳不进入 Agent 上下文，不计作工具成果，也不延长 SDK 请求期限或整轮预算。无需修改 vendored 内核或关闭底层超时。只读查询、Bearer 鉴权、单写入者和取消时等待活动工作清理的约束保留。

当前 MCP 调用期限来自 `max_run_seconds + 30` 秒；额外 30 秒供关闭清理，整轮 watchdog 仍按 `max_run_seconds` 停止运行。`model.timeout_seconds` 只控制模型请求，`limits.timeout_ms` 只控制单次来源查询。调大这两个配置不能修复等待响应头的 300 秒限制。

关闭工具服务采用显式取消标志，不能把真实预算截止时间改成当前时间。取消会阻止新查询并中止活动查询；真实截止时间未到时，不得因清理过程生成 `run_time_budget_exhausted`。传输失败与取消分别记录，仍不自动重放执行结果未知的验证或发布。

保留上游的 Agent 循环、压缩和会话检索。给摘要更合理的独立输出额度，并要求检查点保存草稿编号、修订、证据和待办，不复制完整 YAML。失败摘要不能成为新的检查点，工作窗口配置仍由用户决定，不统一强制改成 128K。

`read_workspace(draft_id)` 对大草稿返回摘要与材料地址。`read_material("draft:<id>", page)` 和 `read_material("validation:<id>", page)` 可分段重读完整 YAML，返回 `material_revision` 与 `next_page`。拼接前检查版本一致；已保存内容直接重读，历史会话只用于找未保存的推理。不能用历史摘要充当已签发证据。

## 4. 继续运行与从零运行

工作台启动 API 接受 `run_mode: continue | fresh`。默认 `continue` 兼容原行为：使用当前成果目录，读取已保存草稿与证据，重新核对适用性；这不是恢复某个正在执行的线程。

`fresh` 使用新的 `output/generations/<run_id>` 目录，既不载入旧草稿，也不载入旧会话索引。授权数据源、知识文档、目标和保存的模型配置仍采用本次启动快照，不复制凭据。旧运行、旧发布及轨迹原样保留；新运行失败也不把旧图伪装成本轮产出。

项目指针决定当前画布和默认后续运行使用哪个成果目录。运行记录保存其自身的模式和输出路径，避免查看旧运行时被新指针误导。启动前拒绝同项目并行运行；启动失败恢复指针。新一代已经启动后，即使没有出图也保持其真实空图状态，历史通过旧运行记录访问。

## 5. 验收范围

本轮回归须覆盖：完整来源支持与冲突语义不变、固定低内存用例不退化、计量成本随贡献增长、大草稿分页完整恢复、诊断总数与持久化一致、耗时工具不阻塞事件循环、失效工具有界退出、从零工作区隔离与历史保留、前端模式提交。

本地替身数据库和脚本模型能够验证这些程序行为，不能证明客户的 462 个名称冲突已经解决，也不能证明 179 个映射在现场数据库能够按期完成。客户复测仍须核对新运行的生效预算、验证诊断、发布成果以及业务目标覆盖情况。

长请求回归另行启用，使用实际 Harness、原生 Node fetch、生产心跳间隔和本地脚本模型，单次验证持续 310 秒，不调用外部模型：

```bash
LIGHTGRAPH_TEST_HARNESS=1 LIGHTGRAPH_TEST_LONG_MCP=1 .venv/bin/python -m pytest -q \
  src/lightgraph/tests/test_construction_harness_integration.py \
  -k survives_default_fetch
```

该用例验证超过 300 秒仍能收到一次完整结果；短期限用例验证心跳不会绕过 SDK 超时，生命周期用例验证断开后不重复执行、关闭后无悬挂写入。通过这些测试也不代表客户的实例映射或名称冲突已经通过业务验收。
