# 从表字段认识到对象与关系：本轮修改方向

## 依据与取舍

用户六点建议作为本轮主线。两份评审的流程建议有效，但其引用的“52 次无效提交、只发布一条层级规则”属于较早的 repaired 实验。最新 review 实验为 107 次调用、31 次无效提交、五条暂存规则、零发布；直接问题是编码被用作名称、有效草案互相冲突、层级发现退回列组，以及跨规则检查发生在探索额度耗尽之后。

采纳以下方向：物理结构先行；候选字段与对象认识独立于聊天保存；以 JSON 明确绑定字段和值；名称与编码在对象建模时分开；对象身份与出现位置分开；关系候选按已知字段角色组织；画布连续展开，不让翻页切断关联。

不采纳以下绝对表述：两三行即可确认全量身份；所有层位都是同一种对象；同名同码即可跨表合并；属性有交集就拆对象；值重叠即可发布业务关系；后续 Agent 只能相信旧认识；固定 4000 节点就是渲染技术分界。旧认识须随证据修订，候选始终不能替代独立语义与完整数据验证。

当前样本和查询结果已有列标识/列名，历史裁剪按完整工具交换进行，不会故意保留裸行而删去同一结果的列头。数据呈现仍有改进空间，但不能把本轮名称冲突归因于输入没有列名。

## 目标流程与实施边界

1. 读取授权物理结构，建立带版本依赖的 SchemaKnowledge。记录字段组、候选键、名称/别名/范围/层位、已验证规则映射、候选关系和未决项；只保存授权字段、结构映射、证据引用、固定状态和计数，不保存原始样本或聊天。
2. Agent 在提交可执行规则前登记并复用对象字段认识。认识可以修订，默认是候选；全量验证或已有有效规则才提供更强状态。元数据、文档、目标或权限变化时失效。每轮输入中保留当前对象摘要，不能靠旧工具消息维持它。
3. 模型数据协议保持严格 JSON；列描述包含稳定 ID、可读名、类型和来源，行与列对应明确，保留空值、数值类型、联合元组和截断信息。原始值只在当前调用内存中使用。
4. 提案支持显式替换同一草案：旧版本只在新版本完整通过入口校验后撤换，失败保留旧草案；替换不能取消既有排除或语义审查义务。诊断使用每个字段自己的错误码。
5. 发现阶段利用已登记字段认识识别编码/名称误映射。真实无名称对象仍允许编码显示；不凭列名替模型自动决定业务含义。首个对象计划包含已识别的英文名和别名，不把全部属性工作推迟到 coverage。
6. 在已验证对象、字段角色、声明外键和兼容编码域上生成有界关系候选，提供范围与遗漏计数；候选经现有引用/FD/完整投影和语义审查后才能发布。保留未知字段的探索入口，避免只沿旧关系搜索。
7. 跨规则一致性检查和修订先于可选关系探索；发现计数包括后续增补。保留整组原子发布与冲突保护，不通过忽略错误来出图。
8. 业务画布使用连续视图：小图完整展示，大图有界概览、搜索定位和邻接展开，保留已加载节点位置、状态、范围和来源详情；后台仍可分批读取，界面明确加载范围。

已有 relative_path、多位置/多支持、属性增补和共享域冲突保护继续使用。原始完整路径分组不能仅凭边可达性推断，本轮展示明确区分图中路径和来源支持；完整路径证据算子的新增必须保持源值不留存与现有身份契约，不能用复制节点代替。

## 验证

针对已复现失败补回归：字段认识跨调用/重启保留与版本失效；授权变更不泄露旧字段；原始值不落盘；同目标草案修订及无效替换；code/name/alias映射；跨规则冲突先于耗时关系探索；候选搜索有界且不自动确认；跨页邻接在同一画布连续呈现。

运行 Python 全量回归、前端测试和生产构建，另用原五表数据/Gold做无模型固定规则对照。保留旧实验与输入，不更改 Gold。用户随后明确要求“修改完了同步到 GitHub，然后直接进行测试”，因此本地验证通过后同步主分支，再从已提交代码冻结并启动新的全量模型实验。继续使用 240 次模型调用、7200 秒总时限，累计 tokens 不限；单次输出长度和内存保护保留。

完成后在本文记录实际实现、测试结果与尚未验证的范围，不把离线通过说成自动发现已验收。

## 已落地的行为

- `SchemaKnowledgeLedger` 在结果库保存版本化字段映射与对象候选，按授权结构、目标和文档版本刷新。Agent 可登记和修订对象认识；后续调用及同项目后续运行重新读取，候选、局部验证、发布和冲突状态分开。保存结构、状态、计数与出处，不保存查询行或临时样本。
- 模型看到的查询行改为列名绑定的 JSON 对象；重复 SQL 别名使用位置键并附原始列名，避免覆盖值。底层验证仍保留有序元组与完整性信息。
- 同目标草案只能显式替换，失败保留旧稿。已登记对象认识辅助发现编码/名称误映射；字段级错误保留自己的错误类别。普通实体和层级均可保留多个别名列，额外英文名必须有明确映射。
- 关系候选由字段角色、已验证类型及声明外键生成，复合外键保留有序列组。候选数量与遗漏明确记录；同表角色重复还使用已验证绑定中的实际值匹配计数。此索引本身不做跨表全列 DISTINCT 扫描，也不把匹配自动升级为业务关系；完整引用与 FD 检查继续由受控工具和执行器承担。
- 全图一致性检查和修复先于可选关系探索；角色出现线索仍可启动关系调查。共享冲突解决后，清除该检查导致的失效标记，不要求原本正确的规则为了清除错误而改写。报告分开记录初始发现、新增或修订规则、全部候选和暂存数量。
- 画布在同一视图加载节点，支持搜索、定位、缩放和平移；较大视图使用 Canvas，按邻接有界展开，保留已加载位置及跨批次边。范围和状态同时展示。完整来源路径分组、自动拆分身份裁决及大型图性能验收不属于本轮已验证能力。

无模型固定对照：`runs/fruit-clean-v2-control-schema-first-20261030/summary.json`，全图 462 节点 / 930 边、12 个跨表共享概念；层级、英文名、独立概念、联合组合的声明指标全部 exact，上下文名称与编码检查通过。数据与 Gold 未修改。

## 提交前验证结果

- Python 全量：2132 passed，82.93 秒，含新增的字段认识、名称误映射、替换草案、多个别名、复合关系候选、跨规则修复顺序和权限回归。
- 前端：151 项通过，生产构建通过；Chrome 实际渲染并定位 450 节点 Canvas 视图。画布每次最多保留 4000 节点 / 16000 关系，明确显示已加载范围；尚无社区聚合、边捆绑及大规模性能结论。
- 依赖完整性和 `git diff --check` 通过；生成的静态 JSON Schema 与类型模型一致。
- 五表初始提示离线检查均低于 262144 字节上限，模型调用为零；输入清单 19 个文件的哈希一致。
- 固定规则对照只证明执行路径与呈现约束；新自动发现实验需单独检查最终发布规则、业务事实和独立评分。真实 Gauss/MySQL、客户 Gold 与生产规模仍未验收。
