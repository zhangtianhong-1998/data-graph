# 从已发现的解释生成执行映射

先确认你要表达的对象身份、属性来源和关系，再读取 `read_material(name="draft_schema")` 获取当前字段。不要凭记忆猜字段名、枚举或证据格式。

## 草稿与执行规则

草稿是带目的、解释、证据引用和未决内容的 YAML 文档，`entities` 描述对象身份与属性来源，`relations` 描述关系端点及有效配对。只声明目标和证据支持的含义，不能将所有对象兜底为指标或报表项。

实体和关系的类型名由当前资料决定。两种映射都支持可选的 `applicability`（旧名 `business_context`），用于记录这条描述成立的条件。省略后按范围未知处理。

使用当前 `draft_schema` 定义的新映射，不提交旧 RuleSpec。数据源、列选择、对象类型、作用域和关系名称由当前分析产生；用户无需手写这些内容。

实体定义含 `type`、`description`、`key_names` 和 `mappings`。每个物理映射指定 `source_id`、`schema`、`table`、`key_columns`，可指定 `label_column`、`english_name_column`、`description_column`、`alias_columns`、`properties` 和 `predicate`。`key_names` 表达身份键角色，`key_columns` 按相同次序指向实际字段；不同位置或表可以提供同一类型的多份映射。

补充已有对象的属性或关系时，先核对已发布草稿中的来源、完整键、对象角色和适用范围。四项一致时沿用已有类型、键名和身份声明，给新关系保留它自己的来源。跨表出现相同编码时，查阅共同字典或键映射；依据不足时分别保留。

名称、描述与身份分开定义。确认的英文名列绑定到 `english_name_column`，行级描述文本绑定到 `description_column`；未知或没有独立列时保持为 `null`，不要从别名强猜英文名，也不要把物理表列注释当成具体实例的描述。没有单独名称列的关联对象，可以声明 `display_columns`（显示项名到来源列的映射），或使用实体的 `display_mode` 按可见关联对象生成显示名称。具体字段以 schema 为准。不要拿复合身份键的最后一列当作整个对象名称，也不要为显示而改变身份键。

有可靠名称列时明确设置 `label_column`，经确认的其他名称设置 `alias_columns`。未指定主名称时，展示组件会拼成“类型（字段：值）”，再缺少组件才使用关系或身份兜底。组件不会自动成为主名称或别名。校验返回的名称质量提示供修订使用，不要求无名称对象编造名称；同一身份出现矛盾名称应修正身份范围或来源解释，不能把名称改成展示组件掩盖冲突。

关系定义含 `type`、`description`、`source_type`、`target_type`、`mappings`，并按语义选择 `allow_self_links`、`acyclic`。物理映射通过 `source_key_columns`、`target_key_columns` 指向端点键，可含属性与筛选。`equal_endpoints` 明确同一行两端身份相等时应报错、忽略该配对还是保留；选择应有数据或文档依据，不能为通过验证随意忽略关系。

有材料或字段映射支持层级关系时，在关系定义里记录 `hierarchy_orientation`。起点是父级时填 `parent_to_child`，起点是子级时填 `child_to_parent`，普通关联填 `none`。沿用来源材料能支持的关系名。一条多跳路径可以包含多种普通关系；沿层级查找子节点时，才使用父子方向。

多个单元读取同一张层级表时，用来源中的完整键和值标识成员，保留每条父子边两端实际使用的列。若还要把列位置记成映射常量，可直接引用对应的物理列名。资料中有独立含义的层级、项目、版本或编号体系按原值记录。这样各单元即使用不同关系名或相反方向表达同一棵树，合并时也能逐条对回原始位置和适用范围。

引用工作表位置时，优先使用原始列名。隐藏列和列权限会改变预览中看到的列顺序，只有原始表头能确定工作表的绝对列号。项目、版本或其他限定条件写入对应的范围映射或筛选条件；行上下文保留来源中能还原路径的列。

若端点身份需要查找，增加 `source_lookup` 或 `target_lookup`，包含 `source_id`、`schema`、`table`、`match_columns` 和 `key_columns`。关系本行对应端的键列提供匹配值，查找表的 `match_columns` 按顺序匹配，再用匹配行的 `key_columns` 形成端点身份。可指定 `predicate`、`cardinality: one|many` 和 `on_missing: error|omit`；默认缺失和多身份匹配都报错。`many` 只用于业务允许的多匹配，`omit` 必须有目标或材料依据，省略数量会报告。相同表也可作为查找表，用于等值自连接。

两端同时声明 `many` 时，执行器在同一张授权明细表上同时投影两个端点键，仅为实际同一行的配对建边。例如同一批次含 A1→B1、A2→B2，结果只产生这两条付款关系。若两端分别来自不同的多值清单，请提供记录双方的明细映射；缺少配对依据时会得到 `lookup_joint_detail_required`。

例如订单只含客户邮箱，客户表才有客户编号：订单映射的 `target_key_columns` 选择邮箱，`target_lookup.match_columns` 选择客户表邮箱，`target_lookup.key_columns` 选择客户编号。客户身份仍用客户编号，不为了套用映射而改用邮箱。指定目标来源后，必须找到该来源的实际匹配行，全图已有同编码节点不能替代这个检查。

查找条件必须包括真正需要的组织、版本或其他匹配范围；显示名相同不构成身份相等。多来源采用各自只读快照，不宣称分布式同时点。任意不等值或时间区间 JOIN 尚不能用等值查找表达，应记录实现缺口，不能伪造配对。

业务属性用 `properties` 指定实际提供值的表列。`constant_properties` 保存草稿声明的固定注解，字段名必须与业务属性分开。业务资料要求某一属性区分对象时，用 `identity_qualifiers` 将实际属性名映射到资料中的口径名。各表可以使用不同属性名，人工裁决时会核对同一口径的值。层级位置常量可以用任意属性名，用 `hierarchy_position_roles` 声明它对应的实体位置（`node`）或关系端点（`source`、`target`、`parent`、`child`）。归并时还会核验常量值与物理位置。映射已记录来源、键列与端点列，无需再把它们填入属性。需要保留同一行的配对时，在相关映射的 `context_columns` 中填写对应的授权列。执行器按来源与列值生成 `row_context.id`，并在每份支持中保存 `values`。内容相同的多行可以共享上下文。

需要还原表内路径时，行上下文应包含路径所有身份列及必要范围列。同一个成员可以出现在多个层级。分别记录每个位置的关系类型、端点列及行依据，可避免拼出原表中不存在的路径。忽略同码自环时仍应保留实体的行支持，以便核对重复位置。所有上下文列同样受表列权限、排除列和访问范围约束。

## 根据数据选择映射

| 已得到的解释 | 映射需要说明的内容 |
| --- | --- |
| 多列共同描述一个对象 | 身份列、作用域、标签、别名、属性和必要投影 |
| 多个位置描述同一类对象的路径 | 各位置的编码及名称列对、位置含义、方向、填充与缺口处理、身份范围 |
| 每行提供父子字段 | 两端身份与字段、适用范围、层级体系及有效配对 |
| 一个对象引用另一对象 | 两端已知身份、连接列、方向、角色、必要限定条件 |
| 同一观测包含独立概念与角色 | 各概念的身份、属性和来源，观测粒度以及参与关系；不把参与概念拼成新的概念身份 |

具体支持的算子名称和参数以返回的 schema 为准。无法表达某个已发现关系时保存实现缺口，不伪造另一种规则来通过格式检查。

## 执行前检查

字段必须来自授权来源，所有物理位置明确使用实际列名。检查键列和标签列是否错位，命名空间是否属于对象身份范围，属性和别名是否已包含在投影中。

规则中的证据引用说明依据来自哪里，引用存在并不自动证明说明正确。源数据结构验证只能确认所检查的约束，不能让 Agent 自行声明业务语义已获批准。

调用 `save_graph_draft(yaml_text)` 后可先执行 `validate_graph_draft(draft_id, mode="structure")`，检查字段、权限和匹配参数而不查询事实。完整实例使用 `mode="instances"`；未传 mode 时采用项目 construction_target（默认 instances）；`predicate` 声明本次实例范围。读取诊断后修改具体失败项；需要更多材料就继续探查。保留正确部分和未决说明，不为获得“成功”状态而删除用户目标中的关键关系。校验返回独立产物和验证编号，不再覆盖先前成功图。

## 产物与后续处理

执行故障不等于建模反证。按返回的来源、阶段和 database 类别处理；unknown 不能猜成超时或永久封锁。只有明确标记可重试时才有界重试，断线需恢复连接并重新验证能力。不要仅为绕过故障删除来源、把主名称降为别名或缩减用户要求的路径上下文。检查 save_graph_draft 返回的 revision_advice；合法缩小目标须有依据，未满足的要求仍保留。

一次性投影缓存会在最后一个使用者完成后释放，图本身及完整来源支持仍受内存约束。确实超限时保留原方案并说明资源缺口，不能靠丢掉上下文把原目标报告为完成。不同实体类型的相同编码不是自环；同名不同码不是名称冲突。

工具回复中的 `query_budget` 是整轮所有来源共用的累计查询与返回量账本。`max_returned_rows` / `max_returned_bytes` 约束源查询已经返回的行数和估算字节，`null` 表示该项不限；它们与工作内存、磁盘、MCP 响应大小和模型 token 分开。开始探索及实例验证前检查剩余额度，投影只选择目标需要的身份、名称、属性和上下文列。分批验证、重新查询或释放内存都不会重置累计量；分批只能减少同时驻留的内容，重复读取还会再次计费。

`returned_rows_budget_exhausted` / `returned_bytes_budget_exhausted` 表示本次读取未完成。即使同时存在名称冲突，也不能把它当作仅有名称冲突的完整验证发布。保留草稿、证据和已独立验证的成果，按工具要求收尾，等待用户调整相应累计额度后在新运行继续。不要为了通过预算删除维度、度量或路径信息，也不要反复尝试发布不完整验证。

行对象用 `key_columns` 的实际值作身份；列定义对象使用 `kind: metadata_column`，身份是来源、Schema、表和列，不是该列里的金额或其他值。目标需要度量等列级语义时，先读取 `reference:metadata-objects.md`，用已读取的授权元数据或适用文档建立对象及其关系。不要求另有定义表，不把所有 NUMERIC 列自动认定为度量。`constant_properties` 仍不能改变行对象的身份。

`predicate` 支持 `is_not_null`、`is_null`、比较、集合和逻辑组合，不限于等值。语法与完整 YAML 示例见 `reference:predicate-guide.md`。若编码为 NULL 的行不代表某个维度成员，保留非空编码范围的维度和关系；指标等其他对象不因此删除。不得未经身份验证改用名称作键；空字符串与 NULL 分开处理，明确记录筛选范围。

跨源 `check_reference` 的本地工作集受 `max_working_bytes` 控制，返回模型的响应窗口单独限制。检查失败时读取 `working_memory` 的阶段、估计峰值和限额；不要把响应窗口、数据库扫描成本或 LLM token 混为同一种预算，也不要用未完成的部分计数宣称引用已验证。

使用 `read_workspace` 检查保存版本、验证和候选结果。不要仅依据自己的最终文字或 Harness 正常退出宣称完成。

你负责依据证据判断草稿是否解释了用户目标，工具负责数据验证与发布检查。当前修订通过验证后可调用 `publish_graph_draft(draft_id)`，发布其固定读取时点的实例图；刷新数据库是新的一次验证。需要选择历史成功验证时使用返回的 `validation_id`，说明该版本范围，不能掩盖后来发现的数据矛盾。结构目标使用 `publish_graph_draft(draft_id, mode="structure")`，报告结构与映射已发布、实例尚未执行。语义评估标记为 `agent_authored`，不要把发布状态称为独立语义 Gold 验收。长期工作区及运行轨迹由用户管理，不在结束时清理。

## 冲突定位与部分发布

如果各表的产品编码采用相同口径，先把不同物理编码列映射到同一组业务键。跨单元合并时，项目可以用 `fusion_policy.entity_rules` 显式指定原实体类型、统一实体类型、共享身份域和完整的键映射。产品编号只在地区内唯一时，把地区也列入身份键。已有节点同名只能作为核对线索。

声明工作表和数据库共用一个 `identity_domain` 时，在 `identity_evidence_refs` 中引用能说明两侧编码体系及适用范围的依据。表级探针可以定位来源，编码值清单可以检查交集。若证据只确认了几个具体对象，就只记录这些对象的对应关系，其他编码保留各自的来源和口径。

并行单元使用不同宽表时，在本单元获准读取的资料中查找实际身份依据。它可以是同一物理对象的重复观察、明确的共享目录，也可以是业务说明中对完整键及其跨表含义的明确约定。核对原文适用的来源、表和完整键列，读出工具签发的带修订号段落引用，再写入实体定义。相同的域名文字、同码同名样本或两次表级探针不能单独证明跨表身份。

普通中文材料无需先由资料作者改写成 YAML。原文明确说明各来源共享同一编号体系时，Agent 可在实体的 `identity_explanations` 中记录解释。每项绑定一个完整物理键和已完整读取的区段，`quote` 必须逐字复制连续原文；`key_roles` 按物理键顺序填写原文实际写明的含义。标识体系有版本时填写 `version`，不要填文档文件修订号。以下示例同时说明字段含义、跨系统共同编号和唯一性，可在实体声明 `identity_domain: 集团设备标识` 并引用该节后补充：

```yaml
identity_explanations:
  - evidence_ref: <read_material 返回的实际区段引用>
    source_id: <实际来源>
    schema: public
    table: <实际表>
    key_columns: [asset_code]
    key_roles: [设备编号]
    quote: 字段 asset_code 对应设备编号。集团设备标识由各系统共享同一编号体系，在全集团唯一，相同编码代表同一设备。
```

工具核对引用、原文、表列绑定和适用于该键的其他条款；未引用的独立编号、条件或版本限制也会阻止共享。两份材料各自写“客户编号全局唯一”不足以确认使用同一编号体系。当前文本核验只接受明确的跨来源共享声明；否定、未核实、目标、规范要求、举例或未识别的措辞会返回待审，不能改写原文以迎合检查。解释随新草稿和验证版本保存，不改写旧检查点。`identity_evidence_state` 区分材料缺失、存在但未引用、已引用但尚未形成解释及已验证共享键；失败诊断指出引文、键绑定、条件或反证所在。根据这些区别补读或修订，不要反复提交相同草稿。

两分支无需使用相同选表、文档或授权指纹。合并器逐份核对冻结支持的实际表列与隔离域，并保留各份权限和业务范围；拥有同一对象身份不等于读者能访问另一份观察。多方合并须存在适用于整组的共同身份依据，A 与 B、B 与 C 的局部相似不能代替 A、B、C 的整组核验。普通属性和服务关系可以补充；身份口径、父级约束和人工判异仍需分别检查。

目录维护者可以在 Markdown 开头的 YAML 中为某一节声明身份域、编号范围及每张表的完整主键。以下示例中，两张表都允许使用“目录规则”这一节；各分支只会读到本单元可见表列的绑定。

```yaml
---
id: parts_directory
purpose: data_description
scope: {tables: [inventory.public.stock, delivery.public.lines]}
sections:
  目录规则:
    identity_contract:
      domain: 备件目录
      scope: shared
      key_columns:
        "inventory:public.stock": [sku, edition]
        "delivery:public.lines": [part_no, release]
---
# 目录规则
库存表和交付明细按同一版备件目录登记。零件号和版次共同确定备件。
```

库存表和交付表也可以各用一份字典。若两份字典均引用同一版外部目录，各自保留本表的 `key_columns`，由资料作者在本节的 `identity_contract` 下填写以下四项。每一项 `key_roles` 对应同位置的物理列。各分支读取并引用本表章节，即可对照签发机构、目录编号、目录版次和完整键角色。两份原始章节的引用均保留。

```yaml
registry:
  issuer: manufacturing-board
  catalog: parts-register
  version: "2026.1"
  key_roles: [part_number, edition]
```

目录编号在签发机构内唯一。将本地文档修订号填到 `version` 会把目录和文档的版本混在一起，请填两份资料实际引用的目录版本。缺少该版本、存在冲突条款或无法核实完整键时，保留待审。

每份实体草稿的 `identity_domain` 应对应本表字典的声明，按声明顺序映射完整键，并在 `identity_evidence_refs` 引用实际读完的这一节。两份字典可以对同一外部目录使用不同的本地名称。保存草稿时，若范围为 `unknown` 而已授权材料恰好声明了本表完整键的共享范围，工具会返回可读取的章节。核对后可修订草稿；资料缺失时保留原范围。各表独立编号时，目录维护者可声明 `scope: source_local`。另有适用于这一键的章节给出本地编号、不同的域、增加或省略身份限定列，或其中的限制无法判断时，工具保留独立身份；核对时应一并引用并记录分歧。共享声明由资料作者提供；抽取 Agent 记录版本、字段和引用，不能代填目录批准。历史章节摘要可用于追溯原文。没有结构声明的旧资料仅在能确认单字段明确且无条件的共享编号声明时支持自动合并，其余保留待审。

同一身份的不同名称按项目的 `label_conflict_policy` 处理。默认 `retain_variants` 保留各名称及来源。属性别名用于已确认含义和单位一致的字段。两张表的同名属性口径不同时，可分别用 `source_id.schema.table.原属性名` 指定规范属性。城市、期间等会影响数值含义的字段可通过 `context_columns` 留在同一条来源观察里。`strict` 要求先解决名称冲突。`quarantine` 可以发布无冲突部分。`validate_graph_draft` 返回 `publishable_subset` 时，可发布无冲突部分；冲突节点及其相连边保留在候选中。全量验证仍记为未通过，不能宣称目标完整。`conflicts:<draft_id>` 提供已保存的编码、名称及映射来源，历史修订会明确标注；`publication_conflicts` 提供跨草稿冲突证据。修复后重新验证与发布会重新计算隔离集合。身份含义、别名解释和筛选条件仍需业务证据，不能按诊断名单直接删行以消除错误。
