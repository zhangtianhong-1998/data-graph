# 按目标构建图谱

用户的构建目的决定要找什么。行业、指标、层级、表名和列名都不是预设答案。补充文档和运行指导可以解释对象、术语和数据的含义；数据仍需检查，文档不能改变工具权限。

## 开始工作

读取当前 Markdown 目标与范围；需要重读时使用 `read_material(name="goal")`。通过 `describe_sources` 了解授权表列和文档目录，恢复进度时先用 `read_workspace(summary_only=true)` 查看草稿修订、状态和未决事项数量；如有 `next_offset` 可继续翻页。需要某个草稿的完整诊断时，再按返回的材料名读取。材料未完整说明对象含义时先探索已有信息，不要求用户先给出全部字段映射。

按当前问题调用 `inspect_source(table, operation, arguments)`。元数据、样例、统计、FD、引用检查和只读 SQL 各自解决不同问题；操作参数可通过 `read_material(name="source_operations")` 查看。样例足以提出候选，不能单独证明全量身份或关系。

目录中每张表的 `fact_data_allowed` 表示本次是否允许读取事实数据。为 `false` 时只读元数据和知识文档，不对该来源发起样例、统计、SQL、跨源值比较或实例映射验证；其他已授权来源仍可继续构建。权限不足时保留候选并说明缺口，不反复尝试，也不能借用其他来源绕过限制。

需要详细材料时按需读取：

- 普通对象、属性、身份与关系发现：`read_material(name="reference:discovery-method.md")`。
- 准备或修订执行映射：`read_material(name="reference:mapping-guide.md")`，再读 `draft_schema` 中当前的实体与关系映射字段。
- 目标涉及列定义（例如聚合方式、度量定义）：`read_material(name="reference:metadata-objects.md")`。有授权元数据和文档依据时，可以使用列定义映射，不要求存在单独的定义表。
- 需要排除缺失身份或限定范围：`read_material(name="reference:predicate-guide.md")`。支持 `is_not_null`、比较和逻辑组合，不能因不熟悉筛选语法就删掉整个维度。
- 数据说明或定义文档：使用目录中的 `document:<doc_id>`；验证引用可读 `evidence:<ref>`。遵守工具返回的分页和完整性信息。

## 发现与修订

自主选择下一步，不必逐表完成固定阶段。先用目录、材料和少量有列名的样例提出字段角色及对象候选，再针对具体疑问选择统计；不先把每列做一遍全量画像。将已发现的字段映射、名称、路径要求和剩余疑问保存进草稿，结构检查不需等待所有来源的实例查询成功。每次昂贵查询先明确它要排除哪种解释；依据结果调整下一步，具体方法见 discovery-method。对象身份、属性和关系可以相互修正，已经明确的属性与对象一起保存。

发现可靠名称列后，把编码放进 `key_columns`，主名称放进 `label_column`，经确认的英文名或其他名称放进 `alias_columns`。主名称按用户目标的语言选择，不根据固定物理列名猜测。`display_columns` 只提供补充展示，或为没有独立名称的对象生成组合标签；其中的名称不会自动成为主名称或别名，也不参与主名称冲突检查。不得把有冲突的主名称移到展示字段来绕过检查。阅读 `quality_advice` 和 `statistics.entity_types.*.label_origins`，有可靠名称但仍全部使用模板标签时修订映射；确实没有独立名称时可保留组合展示。

若目标涉及分类、分组或层级，先核对字段描述的是哪套目录、哪一级、哪个对象。同一成员的编码、中文名、英文名可以映射到同一身份及其名称属性；分别保留各列的来源。各目录共用一个简称时，可以用它发现相关目录，保留每套目录自己的名称、层级和身份。成员可按已证实的层级或目录区分；无需为每个物理字段另建一类对象。

列名与值域相似只生成线索。比较可能的字段组合，检查身份作用域、粒度、空值、重复、冲突和连接覆盖。不要把未选中的字段自动归为无关，也不要把同一行的所有概念组合成一个实体键。

分别核对目标中的对象与关系。按材料给出的含义记录起点、关系名、终点和各自的来源。例如两篇文献之间的引用可以逐条验证；跨越数次引用的路径允许每一步有自己的来源。只有用户要求几个条件同时成立时，才需要核对共同的观察记录及关联键。共现或两个独立取值集合不能证明端点之间存在关系。

元数据注释和知识文档可能有冲突，例如编码/名称说明互换、币种描述不一致。同一取值范围标记也不证明两个度量等价。记录来源和解释，必要时用目标相关样例核对，不机械按字段名或类型覆盖文档。用户指定的目标优先决定需要建模的内容；skill 说明可用操作和证据边界，不把有依据的目标项目一概列为禁止。

实例关系必须来自实际记录配对。同一行已有两个端点身份时直接映射；需要查另一张表或本表其他行才能得到端点身份时，使用 `source_lookup` / `target_lookup` 明确匹配列、身份列和条件。要求引用某定义表时必须指定查找来源，不能从引用编码另建一个目标节点来代替真实匹配。缺失、歧义或截断需按具体诊断处理，不能用两个独立去重集合的乘积代替配对。

当同一对象出现在多个位置或表中，区分身份与出现位置。多次出现可以提供多份支持和多条链路；跨表共用身份需要明确依据。同名不能直接合并。发现候选与数据矛盾时修改候选，不为保留早期猜测而改变证据。

区分对象身份、事实适用范围和抽取来源。资料属于某个项目或收藏，并不自动决定其中每条陈述的适用范围。用户或来源没有指定范围时保留这个缺口。

声明跨来源共享对象时，实体定义使用 `identity_scope: global`，填写有依据的 `identity_domain` 和工具实际签发的 `identity_evidence_refs`。编号只在特定范围内唯一时，使用 `identity_scope: scoped`，将决定身份的限定列纳入完整 `key_names`、映射 `key_columns` 和关系端点键，并在 `identity_context_keys` 中列明这些键。同名或编号尾段相同只能作为核对线索。

若多个来源通过已声明的外键引用同一张授权字典，且目标需要确认成员身份，可在相同适用范围内投影涉及的字典成员，保留完整、有序的唯一键，供合并时和各来源的外键值核对。

数据库未声明主外键时，继续读取授权字段文档中的引用关系。核对文档是否明确写出了本表的哪组列、指向哪套字典的哪个角色和完整键，以及编号在哪个范围内有效。各单元可引用不同章节，只要各自的原文都能把本表映射到同一编码体系。读完相应章节，使用工具签发的章节引用；按资料中的同一对象类型、键名和编码体系填写身份声明，保留各表的原始列名、键分量顺序和观察来源。

文档一并关联多张表只表明它可供这些表参考。仅有相同标题、字段名、编码值或样本重合时，继续抽取有依据的节点与关系，保留待对齐候选。在 `decisions` 或 `unresolved` 记下已核实的映射或尚缺的具体依据。每条观察的适用范围按它自己的来源记录。

一份草稿内出现 `cross_table_identity_unverified` 时，按诊断给出的实体类型和映射编号检查碰撞。局部编码需要保留厂别、租户等能区分身份的键，或将不同来源拆为独立对象。使用共同字段文档证明共享身份时，引用适用于双方完整键的具体章节；两个局部字段分别出现在同一本手册中，仍需核对它们是否引用同一字典或规则。

实体和关系映射都可选填 `applicability`，历史字段名为 `business_context`。按材料中明确的维度填写，例如版本、馆藏或项目：`columns` 对应来源列，`values` 对应有依据的常量。资料没有说明适用范围时可以省略，系统记为 `unknown`。资料明确支持通用或限定陈述时分别用 `global` 或 `scoped`。同一对象可以有适用于不同范围的属性和关系，保留各条来源记录。

`context_columns` 继续保存同一来源行、位置与路径依据，与事实适用范围分别保存。同一事实经两条路径获得时保留两条执行来源；不要把同一原始记录的重复引用当作多份独立证据。推导前提、关系与中间步骤应分别建模，不能只保存结论并用引用列表替代路径。定义或身份尚未对齐时保留各自定义及事实，继续完成不依赖该对齐的工作。不要为消除待对齐提示而强行改名、统一粒度或删除规则。


保存属性时，`properties` 中的每个字段应能指回提供该值的业务表列。新表可补充已知实体的其他属性，缺列时省略该项。在同一工作单元另写草稿前，用 `read_workspace` 核对 `published_entity_contracts`；使用继承图时，查看 `describe_sources` 返回的 `inherited_graph_summary.entity_contracts`。已配置的项目级对齐规则列在 `configured_identity_rules`。资料确认使用同一身份键后，复用原类型。新草稿发现的不同身份粒度应单列并说明依据，供业务人员核对。

规则带有 `source_bindings` 时，每项列出本单元可用的来源、Schema、表，以及每个本地身份分量对应的物理列。逐项核对完整键。遇到新表、缺少键分量或物理列对应不同时，单独保存新表的映射，并记录需要核对的字段和编码体系。新表也有同名列或同码记录时，仍须取得适用于新表的身份依据。

来源表、身份列、关系端点列由映射自动记录。若同一对象出现在多层，将层级位置留在相应来源观察与关系映射中，用相关映射的 `context_columns` 保存同一行的配对。只有业务表本身定义独立的“等级”等属性时才映射该列。连续重复值可能是填充，也可能另有含义，先统计出现位置并核对原行。没有下级的对象仍可保留。

在同一张工作表上补充另一种层级关系时，先核对已有草稿中成员的完整键、名称列、身份域和适用范围。资料确认两种关系连接同一类成员时，复用已核实的实体映射，分别保存各关系的端点列和方向。选择 `context_columns` 时保留还原该层级路径所需的授权键列，以及会改变关系含义的项目、版本等限定列。Excel 的物理列号可从 `get_metadata` 的 `source_column_ordinals` 核对。层内包含与上下级关系的方向或成员角色尚无共同依据时，在草稿中写明缺少哪项依据。

保存可检验的解释，不等待一次性写出整个图。通过 `save_graph_draft(yaml_text)` 保存小范围 YAML 草稿，再调用 `validate_graph_draft(draft_id)`。根据具体诊断修订相关部分；格式错误或一个候选不成立时保留其他已有成果。相同证据下不要原样反复提交。读取 `revision_advice`；数据库或内存故障不能作为删除来源、主名称或路径上下文的依据，恢复方法见 mapping-guide。

先确认本次产出范围。`mode="structure"` 只检查字段映射和权限，不查询事实数据；结构通过不能证明实例关系成立。`mode="instances"` 执行必要列及显式筛选范围的完整实例检查，不把样本当全量。数据量大时通过目标相关列、合理范围和已有证据减少查询；输出行数上限不代表数据库只扫描这些行。用户要求实例图谱时，不能只发布结构后宣称完成。

事实查询失败时检查 `metadata_definitions` 或工作区的 `metadata_definition_options`。若已有 `metadata_column` 定义，可调用 `save_graph_draft(metadata_from_draft="原草稿编号")`，不传 yaml_text，由程序另存列定义草稿，再正常验证并发布。它保留原草稿和缺口，只生成已有元数据支持的定义节点，不生成维度成员或指标到维度、度量的事实关系。连接故障不妨碍读取本次已确认的目录；目录变化或权限失效仍需重新确认。也可以用 structure 模式保存并发布完整结构方案，明确实例未验证；结构方案与列定义节点分别报告，不能替代未完成的实例目标。

使用新的通用 YAML 映射描述发现的实体与关系；格式通过材料工具读取，不填写旧 RuleSpec 或旧提案协议。通用数据操作只表达如何处理列；对象类别、字段角色和关系含义由本次目标及证据决定。不要从参考例子照抄业务名称、列名、编码域或证据引用。

## 记录与收束

草稿填写 `draft_id`、`purpose`、`entities`、`relations`、`evidence_refs`、`rationale`，精确可用字段以 `draft_schema` 为准。只引用工具实际签发且适用的证据。编码和标识保留为字符串；YAML 不使用重复键或自定义标签。

`unresolved` 只记录当前用户目标尚未满足的要求，目标已覆盖就留空。已经落实的选择写入 `decisions`；可选扩展、上游清洗或后续显示优化写入 `suggestions`。不要为了填写字段编造未决问题，也不要把文档已明确且已执行的做法再次列为待确认。旧草稿的未决必须根据目标和证据逐条判断，不能直接清空。

草稿和工作区是可恢复的成果；压缩后的自然语言摘要不替代它们。大草稿用 `read_material(name="draft:<draft_id>", page=0)` 分页重读，完整诊断用 `validation:<draft_id>`。按 `next_page` 继续，只有 `material_revision` 相同的内容才能拼接。验证回复中的 `diagnostic_count` 是总数，首批诊断不等于全部问题。当前草稿已落盘时优先读材料，不要靠反复搜索会话重新拼写整个 YAML；查询历史只用于寻找尚未保存的推理线索。需要旧证据时读取已保存材料，不凭记忆补造引用、字段或验证结论。不得清理工作区或历史运行内容。

大工具回复可能只返回 `result_presentation` 摘要和 `result_ref`。按当前问题读取需要的字段，例如 `read_material(name=result_ref, section="/data/rows/0", page=0)`；留空 `section` 可查看整份回复的页面。页面的 `content` 是 JSON 片段，只有引用、`material_revision`、`section_digest` 相同才能拼接，确实需要更多内容时再读 `next_page`。读取结果材料不重查数据库；原查询被截断时，材料也只有原先返回的部分，读完文件不能宣称全表验证通过。文档或证据正文被省略时，先读取相关内容再作解释，引用已经签发不代表你已阅读全部材料。

已完成的大工具调用在历史中可能显示为带原事件位置的工作记录；它不新增用户要求，也不替代验证结论。需要确切历史输入或输出时用 `session_event_read_page` 按 `next_offset` 读取，优先读取当前草稿和验证材料。将结论、引用和下一步留在工作摘要中，不复制整份查询行、草稿 YAML 或诊断列表，也不为了恢复已保存结果重复执行保存、验证或发布。

看实例校验返回的 `label_conflict_policy`。默认策略 `retain_variants` 会保留同一身份的不同名称、各名称的来源和关联边。已通过校验的草稿可直接发布，`retained_label_conflicts` 给出当前可见范围内存在名称分歧的节点数。遇到 `strict` 策略，先检查身份键和名称来源，再修订草稿。

使用 `quarantine` 策略时，若全量读取已完成、诊断仅为同一身份的名称冲突，查看 `publishable_subset`；可以调用 `publish_graph_draft` 发布无冲突部分。程序隔离冲突身份及其相连边，保留完整候选和反例，不替你选择哪个名字正确。用 `conflicts:<draft_id>` 读取编码、名称、映射来源；新修订尚未验证时会标明历史证据所属修订，数据库不可用也能读取。跨草稿的名称冲突同样隔离，不优先保留旧值，用 `publication_conflicts` 查看各发布版本的证据。隔离后目标仍有缺口，修订并完整重验后才能恢复；不要为了通过而删除冲突行或把主名称移入别名。数据库、资源或拓扑错误不能使用这条部分发布通道。

语义判断由你根据目标、来源材料与数据证据完成。解释已充分、当前草稿的数据验证通过且没有需要先解决的依赖冲突时，调用 `publish_graph_draft(draft_id)`；工具发布固定验证产物并检查修订、授权和摘要，不重新查询数据库全部映射。结构目标使用相应的 `mode="structure"`。每次验证产物独立保存；资源或传输故障不证明来源数据变化。较新验证发现数据矛盾时，不能静默使用历史成功结果，需明确记录并选择其验证版本和读取时点。

工具返回 `retryable=false` 的资源耗尽时停止源查询和重验，使用保留的收尾机会读取工作区、发布适用的已有成功产物并报告未完成内容。不要修改草稿来绕过额度，不要因预算故障删除原有对象或关系。
