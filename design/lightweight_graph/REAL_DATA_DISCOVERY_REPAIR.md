日期：2026-10-26。审查起点：`81d04b2dde8f4c203a9d0f1ad672cd9be89f1bc0`。本轮针对用户报告的“部分完成、没有业务图、无法发现关系”修复协议和调度问题。

用户提供的运行摘要是 16 列宽表：L1～L5 各有 CODE、CN_NAME、EN_NAME，另有责任中心列；报告包含 10 次模型调用、35 次数据库查询、发现 1 条规则但未发布规则。本轮未读取该次运行目录或真实模型原始响应，没有连接客户数据库或调用真实模型。下面分别记录源码已核实的问题、保护性测试与待复跑范围。

## 反馈的核实结果

| 反馈 | 核实与修复 |
| --- | --- |
| `semantic_review_proposition_mismatch` 阻断层级 | 旧协议要求模型完整回显嵌套提案，遗漏默认字段也会失败。改为编译器保留完整主张，模型返回本次签发的短引用；协议错误最多纠正一次 |
| `unregistered_attribute_semantics` | `english_name` 原本已经支持，自定义属性也可通过 `semantic_schema` 注册。实际缺口包括部分已有业务属性未进入编译允许集合、缺少定义后没有定向修复，以及 `business_code` 身份映射表达不兼容 |
| `builtin_property_definition_forbidden` | 旧实现拒绝所有内置属性重复声明。兼容声明现按引用处理，不覆盖内置契约；属性类型、系统字段和关系方向不兼容时仍拒绝 |
| `no_confirmable_entity_group` | 这是没有规则通过的汇总结果，不能单独定位根因。当前报告保留具体失败，修复过程中保留已经通过的独立提案 |
| 已有实体仍发现不了关系 | 宽层级规则原本未完整进入关系端点目录；现在每个层位显式提供端点，关系提案通过 `source_level`、`target_level` 选择正确实例 |
| `PARTIAL` 或运行结束但业务图为空 | 进程终态、规则发布与业务产出是三个不同信号。报告新增业务节点/边计数与业务图状态，元数据图不再被当作已有业务产出 |

用户摘要中具体哪个属性名、哪个模型响应触发了失败，仍需该次运行配置和安全诊断记录确认。不能仅凭错误码推断是英文名不受支持，或认定目标类型配置一定过严。

## 本轮实现

**语义复核保留，回显协议简化。** 编译器冻结端点、层序、作用范围和条件，签发只在当前复核中有效的 `proposition_ref`。模型判断必须引用该主张；仍检查全部适用文档、已签发证据、反证和未满足条件。旧式完整回显保持兼容，但引用与回显冲突、跨主张重用引用或方向不符不能通过。一次协议纠正共用原模型预算；否定、未决或条件不满足不会反复询问直到得到肯定。FD 通过只能证明字段依赖，不能单独证明父子关系。

**属性定义与属性引用分开。** 内置业务属性和关系的兼容声明会规范化为引用；其描述、类别子集和声明不能改写全局契约。系统元数据属性、错误类型、反向内置关系仍拒绝。`business_code` 若只是重复声明引擎自动输出的身份键则合并；若映射到另一个列则返回 `business_code_mapping_conflict`。陌生属性仍需定义类型与适用类别，排除列和仅供取证的列不能借新名称进入结果。

**提案契约错误可在本次发现中修复。** 编译前执行与规则引擎一致的无副作用检查。缺定义、缺身份列、错误属性契约等可修复问题携带安全错误码和已签发列引用进入新任务；表内提案使用 T5，引用提案继续 T2。最多两轮编译修复，所有调用仍计入原预算。已通过的独立提案保留，不要求模型每轮重新提交全部规则；每条规则只携带实际使用的定义，未使用的坏定义不能使其他对象失败。

修复过程中，已经声明的排除范围只能保留或收紧。FD 等数据反例的原始原因继续进入后续任务，不能被“修复一个属性定义”的上下文覆盖。无进展、轮次耗尽或预算不足时保留具体未决项；未修复的提案契约错误不会写成“该表发现已完成”，下次运行仍可继续。真正的语义否定也不会因被归类为格式错误而重试放行。

**层级对象能成为关系端点。** T2 目录列出宽层级每个层位的键、名称和规则引用；提案明确指定需要的层位。若同一编码同时出现在一级和二级，执行器按指定层位解析实例，不能猜测。缺失层位、未知层位或给非层级对象设置层位均拒绝。关系名称和端点层位进入引用规则标识，因此同一对列支持两种已确认关系时可以分别发布。跨表连接列改名后，边仍使用源实体的逻辑命名空间；不会因连接表的复合列别名形成另一个不可见范围。

**报告直接说明业务产出。** `counts` 新增 `business_nodes`、`business_edges`、`candidate_business_nodes`、`candidate_business_edges`；`validation.business_graph` 为 `entities_and_relations`、`entities_only`、`candidates_only`、`empty`，仅发现规则时为 `not_requested`，读取产出失败时为 `unavailable`。这些值描述当前授权业务视图；终态仍独立表示执行是否完整，不能据此推导语义正确率。存在待重试任务时保留 PARTIAL，语义未决与格式修复未完成分别记录。工作台运行详情和结束提示直接展示业务产出，不只显示进程终态。

## 已有工程证据

`test_wide_table_recovery.py` 使用与反馈相同的 16 列结构和离线 HTTP 模型替身，模拟缺默认字段的语义回显、缺少自定义属性定义、重复内置定义，以及修复时只返回失败对象组。修复后得到 **9 个业务实体、10 条业务边**：6 条层级边、2 条责任中心分配边、2 条另一种业务关系。首次 8 次模型替身调用、11 次数据库查询、发布 4 条规则；重复运行 0 次模型调用、4 次查询，节点和边数量不变。英文名称作为别名保留。可复核输出位于本地忽略目录 `runs/real-data-repair-20261026/wide-table/`，与客户数据无关。

其他保护性回归检查：

- 层级语义被否定时，仍可发布独立责任中心实体，但不发布层级边。
- 全部弃权时，报告业务图为空；元数据节点仍可存在。
- 未修复的属性契约不会缓存为发现完成；下一次提供正确提案后可恢复，随后才复用缓存。
- 同编码跨层位时关系连接指定实例；缺层位或错误层位不能猜测。
- 反向主张、错误引用、遗漏文档、否定依据和模型预算耗尽不能通过协议纠正绕过。
- 修复轮次之间保留排除约束，FD 反例的原始原因不会被编译修复覆盖。

## 待复跑范围

上述结果证明本地模拟输入上的协议恢复、实体实例化和关系生成，不证明真实模型已经能准确解释客户表。用户原运行仍需在修复版本上复跑，核对实际提案、接受/未决原因、规则发布数、业务节点/边、关系支持及已处理范围。真正缺少语义证据、来源权限或预算时，系统仍可能返回部分完成或未决。
