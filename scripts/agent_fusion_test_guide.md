## 完整报告之后怎样验收

### 冻结输入，建立独立答案

从 G 的 `runs.json` 找到 C 的抽取运行和两种合并的来源。如果某档只有离线重放，标明这一点；需要做双提交评分时，才在隔离副本只重跑缺少的合并节点。记录四个上游的完整产物 ID、图摘要、授权和源快照，分别保存确定性合并与模型审查的代码指纹、策略、模型和预算。先记录后面的业务预期，再看新结果。没有冻结的数据库行版本时，把共同快照可核的范围和只能核清单的范围分开。

- 50 个已核实的城市组织码作回归。按来源表、完整键列、带类型的值和名称在 C 中重新定位成员，确认每侧观测仍存在。两个空哨兵分别保留；另一业务轴同串缺名不属于这份目录。43 个探索对及其他未获独立裁决的项记为未知。旧 F 的节点 ID 和模拟清单不能直接跨版本使用。
- 再选未用于编规则的完整业务轴，包含同单元、跨单元以及已知应合但没有进候选的一对。由源记录、权威材料或已有业务裁决判定应合、应分和未知。按抽取单元与原节点 ID 标注。关系另取普通父子、同端点不同物理层级、同码延续成自环、不同明细不得交叉连边的样本，保存源行、端点列、方向和适用范围。没有独立依据的样本单列。全图指标只在真值覆盖相应总体时才计算。

### 在同一批检查点上并行核对三件事

1. **找出可以在哪个阶段修的键。** 用 `scripts/audit_checkpoint_merge.py <C 模型审查运行.json> --node merge_1 --recheck-proposals-only` 复核已进入历史裁决的提议。输出的 `cross_table_check_summary` 按是否共享已绑定的键章节、首项观测检查及整单元授权指纹是否相符交叉计数。没有章节且另外两项通过，是仅在这三项上缺章节的键检查数；同一键出现在两个提议会计两次。章节是否肯定共享身份须另读原文。没有提议、被截断、名称不合、同表同列或同表跨轴的项分别用审查表和逐模式明细对账。
2. **核对“拨备”和收入类。** 对每个要比较的运行，执行 `scripts/audit_checkpoint_merge.py <运行.json> --node merge_1 --include-edge-lineage --explain-name 拨备 --explain-name 拨备13 --explain-name 坏账准备 --explain-name 净销售收入 --explain-name 专业服务收入`。多名称共用一次审计。按单元、草稿、来源表列、带类型的完整键、实际观测名及最终输出 ID 对账。查清“4×23 份输入”与“24 个双份组加 1 个单份组”的分组维度和成员映射。每组核实同物理键、跨表同目录、异轴、口径冲突或待定。对同一节点命中多个名称的情形按 ID 去重。
3. **核对变少的原始边。** 将旧批次和 C 映到同一冻结来源上；边 ID 可以不同，用源身份与快照、原始行或有等效证据的明细键、有向端点列和值、关系断言及适用范围核对。先报有共同来源覆盖的事实数，然后逐项区分同事实多种建模、同码延续策略、覆盖新增/退出、原来支持但 C 漏抽、无法定位。另报 C 新增的无支持事实。核对两个不同业务事实之间即使端点相同也能分别查回。缺少快照或行见证的部分记“无法核实”。4,383 是边数的**净差**，要分别列少了多少、多了多少；2,043 个旧自环也不能直接从净差中扣作已证重复。

### 测量一次真实模型审查的净收益

在同步新版代码的隔离工作区，复用 C 的**同四份**抽取检查点。比较同一版本、同一权限与基础策略下的确定性合并和一次新发起的模型审查合并。已有满足条件的真实提交可复用。离线重放历史模型裁决会重现旧策略；测试截断恢复及新规则的生效必须有新版审查记录。记录首次送审/完成、重试补回、预算耗尽未审、模型提议、核实组、已在基线合并及新合并，并记录调用数、耗时、供应方实际返回的用量。报告“没进入候选 → 未审 → 未提议 → 核验被拒 → 已核实但未新合”的逐阶段去向，分别计模式、键和原成员对。

以下用第一档确定性提交绑定的真值评两份真实提交。已有完整普查目录可直接使用最后一条命令。PowerShell 变量指向本机的实际运行 JSON、两个新目录、真值文件及新的结果文件。真值格式见[逐对评分说明](fusion_census_guide.md#复核错合和漏合)，这里用 `kind=input_entity`、`[贡献单元, 原节点ID]` 指定两端。

```powershell
$py = (Resolve-Path '.venv/Scripts/python.exe').Path
& $py -X utf8 scripts/audit_fusion_census.py run $detRun --node merge_1 --committed-only --output $detDir
if ($LASTEXITCODE -ne 0) { throw '确定性提交核对失败' }
& $py -X utf8 scripts/audit_fusion_census.py run $agentRun --node merge_1 --committed-only --output $agentDir
if ($LASTEXITCODE -ne 0) { throw '审查提交核对失败' }
& $py -X utf8 scripts/audit_fusion_census.py compare-committed $detDir $agentDir --truth $truth --result $result
if ($LASTEXITCODE -ne 0) { throw '请检查真值版本、上游检查点和输入成员映射' }
```

报各业务轴的应合/应分对数、新增正确合并、新增错合、纠正旧错合、新增拆错、两档均漏合、未知和去向未核实。检查候选召回及已有人工判异是否保持。上述命令只评价实体对；关系按前面的独立事实清单评价，再核对各自输入边的来源。模型没有新增归并时，照实报零。人工逐键模拟单列。

### 何时重新抽取

| 现场证据 | 该运行什么 |
| --- | --- |
| 正确观测已在 C 检查点，但未入候选、回复截断、验证或应用时误拒 | 重跑相应的合并实验，可固定模型提议单测验证器。 |
| 原始材料有依据，检查点缺少决定身份或关系的字段、列绑定、适用版本或行见证 | 冻结同批来源，只重抽受影响分支。对比草稿修订前后及签入产物的依据；用同一组新检查点再比较两种合并。 |
| 原始材料也没有说明两个轴是否共用身份 | 记待定并列出缺少的业务依据。重抽同一批材料不会补出业务事实。 |
| 修改了所有分支共用的抽取契约，且下面的正反对照已通过 | 在冻结源上做一次从四分支抽取到合并、发布和查询的完整验收。先等抽取终态，再复用这同四份新产物比较两种合并。同源对照仅切换待测机制；模型版本或读取窗口变化时单列。 |

全流程通过的依据是已知正例得到召回，已知反例保持独立，原始事实、方向、限定条件和来源能逐项对回，且归并没有扩大可见权限。在隔离发布图上用名称或完整码查一次已知应合对象、一次同名异码对象，再查其上下游并打开原始依据。记录返回的唯一对象数、候选数、原边 ID 和可回到的源行。先执行独立语义回归 `.venv\Scripts\python.exe -m pytest -q scripts/acceptance/test_identity_contract_semantics.py`。目前两个反例能复现错合与漏合；修复后四个案例应全绿。发现已证错合或无依据丢事实时保留现场，继续离线诊断，暂缓正式发布。每次交付区分测试输入覆盖、未知和可核实的业务结果。

## 二、新抽取分支，验证 Agent 在定义草稿时做了哪些选择

1. 在另一份隔离工作区用冻结工作簿或其他已获准读取的宽表新建一次并行抽取，至少两分支、同一分支内至少两种可能重叠的投影。优先选已有独立答案的材料，涵盖同码同名、同码异名、互补属性和不同关系方向。记录真实授权、表列和样本版本。没有外键时照实记录。用已有冻结文件即可完成的部分优先执行；缺源权限时列出该项及已完成范围。
2. 逐分支取该次抽取自己的轨迹。记录 `inspect_branch_overlap` 的 tool call ID、成功回执的 `inspection_id`、涉及的草稿与修订号、Agent 看到的来源列及两侧角色。把保存时的 `branch_overlap_preview`、实际展开检查、实际修订定义、修订后验证/发布四件事分列。若 Agent 未调用，明确标“未调用”；缺历史轨迹标“未知”。比较草稿修订前后可证实的实体数、关系、端点和来源，不能归因的变化单列。
3. 让这些新分支进入自己的模型审查合并，复用第一项的核对口径。用“原始分支 → 分支验证后 → 确定性合并 → 模型审查合并”四列呈现。每列标注实测、缺证、未执行或不适用；分支无法复现修订前状态时不要推算节省量。关系分别列原始边、核实的事实及画布连线，单位写在表头。

最后用四句话回答：分支 Agent 实际做了哪些修订；相同输入下合并 Agent 净减多少节点；多少原始关系有证据可归入同一事实；“拨备”从几份到几份、还剩哪些冲突。发生错误或零增益也保留证据。报告完成后停掉本次隔离服务。
