# 探查转提交时提前终止的修复

> 设计状态（2026-11-03）：本页保留原版本的方案、故障与验证记录。当前通用构图目标、Harness 迁移与 YAML 产物规范见 [按用户目标自主构图](GENERIC_GRAPH_CONSTRUCTION.md)。本文的历史通过结果不证明新路径已验收；未被迁移改变的接入、执行、权限及平台约束继续适用。

## 原因

用户反馈单表运行调用模型 7 次、失败 0 次，却没有发现或发布规则，并报 `discovery_steps_exhausted`。本地代码可以复现这条路径；用户另一台机器的原始轨迹未提供，不能据此排除那次运行还有其他问题。

`max_discovery_steps=8` 时，前 6 轮可以探查，第 7、8 轮预留给提交和纠正。代码里的 `steps==6` 表示已经完成 6 次请求，下一次是第 7 次请求。旧实现移除探查工具后，若模型仍返回探查调用，会立即抛出“步数耗尽”，没有使用第 8 轮。

模型请求计数与 Agent 阶段校验分别发生：接口响应可以成功接收、解析，但随后返回的工具不允许在当前阶段执行。所以“调用失败 0 次”不能证明 Agent 已完成提交。

纯文本不走这个工具拒绝分支。合法的 `finish_discovery` JSON 可以结束；非 JSON 文本沿已有的请求协议重试处理，最终可能报 `llm_schema_invalid`。

## 修改后的行为

1. 提交阶段返回探查工具时，整批调用都不执行，包括混在其中的提交调用。已经接收的草案与对象模型继续保留。
2. 返回固定反馈：拒绝原因、执行次数 0、允许的提交工具、剩余轮数。反馈不复制被拒绝的 SQL 或原始值。
3. 每个发现任务最多一次阶段纠正，使用原有剩余轮数，不额外增加探索额度。纠正请求只提供提交工具，并设置 `tool_choice=required`。正常请求继续允许工具提交和小型 JSON 收尾。
4. 真正用完轮数才报 `discovery_steps_exhausted`。有剩余轮数但纠正后仍不按要求提交，报 `discovery_final_response_required`。全局模型调用数、时间、查询等限制继续生效。
5. 默认 `max_discovery_steps` 从 8 提高为 16，允许 1～32；运行配置、模型客户端、预检、schema 和示例统一。显式填写的 8 不自动改写，可在前端“Agent 与模型”的“探索轮数”中调整，保存后下一次启动立即生效，无需重启服务。源工具额度 `max_tool_calls` 仍默认 16。

模型轮数不等同于 HTTP 请求数：请求自身的协议或网络重试可能增加 HTTP 调用，实际每次调用仍计入全局额度。末轮只提交草案而未完成收尾时，草案保留为待处理，不自动声称完成。

## 可观察性与验收

运行报告增加 `discovery_phase_rejections` 和 `discovery_phase_recoveries`。恢复计数只表示模型改用了允许的工具或合法收尾格式；工具参数、草案和语义仍需继续校验，不等于规则已发布。完整轨迹增加“提交阶段工具纠正”，记录允许工具和未执行事实；每次模型请求记录当前发现轮数与阶段，Agent 结束事件记录实际终止码、源工具数和提交工具数。

回归包括：六次探查后第七轮误调用、第八轮成功提交；流式与非流式响应；混合批次不执行；保留旧草案；持续错误、共享调用预算和合法收尾；纯文本请求重试。发布集成测试还检查候选实际编译、执行并发布出业务节点。离线固定响应通过只证明这条修复路径可行，真实数据上的字段理解、语义审查和覆盖率仍需用户环境复跑。
