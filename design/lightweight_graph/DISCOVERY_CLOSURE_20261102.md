# 发现任务的结束条件与重复名称覆盖

本次修改对应 `full-extraction-v2-context-protocol-20261102T085857Z` 的三个问题：关系提案被拒后仍长期挂起、相同资料下重复探索、联合表的三个名称列没有进入来源支持。

## 结束条件

| 情况 | 候选或任务状态 | 对运行结果的影响 |
|---|---|---|
| 关系端点类型不符合已注册关系、键长度不匹配、使用不存在的层位 | 当前提案 `rejected`，保留错误记录 | 拒绝本身不造成 `PARTIAL` |
| 正常提交结束，没有新增关系，也没有未处理的提交 | 关系任务 `resolved` | 正常结束 |
| Agent 弃权、业务依据不足或完成后仍有未解释字段 | 任务 `unresolved` | `COMPLETED_WITH_GAPS` |
| 请求、查询、协议或预算错误中断工作，或者明确还有提交未完成 | 任务 `deferred` | `PARTIAL` |
| 程序内部异常 | 沿用原错误处理 | `PARTIAL` 或 `FAILED`，不伪装成业务判断 |

当前不合法提案的拒绝不证明所有其他关系都不存在。用户可以主动“重新调查”，这只安排一次新的调查，不授予发布权限。普通续跑不重新打开同资料下的已拒绝提案。资料版本变化时，旧候选先失效，再根据新资料判断。

重新调查正常结束、没有替代提案时，旧提案恢复为已拒绝；实际中断时保留待处理，新出现的语义缺口和等待发布的替代规则也继续保留。关系 Agent 会收到已验证的全局身份域，区分同一对象的多来源支撑和不同对象间的业务关系。

关系调查按表结构、适用文档、已验证端点规则版本和角色线索记录结果。相同条件下的未决结论会保留为缺口，不再自动消耗一轮模型调用。显式重新发现、候选重新调查，以及上述依赖变化仍可启动调查。没有来源数据版本标记时，这个缓存不声称数据永远不变；已知规则每轮仍做完整验证，新增关系可以通过重新调查发现。

草案提交仍有明确的结束契约：`finish_discovery` 可以通过 `withdraw_rejections` 放弃失败尝试，失败记录保留为诊断。单独填写 `pending=false` 不能把未处理的拒绝伪装成已修复。显式 `pending=true`、未完成提交、截断或预算中断继续报告 `PARTIAL`。

## 三个名称列如何处理

联合表中的“指标名称、产品名称、渠道名称”已有对应定义表提供名称。仅凭名称相同不能认为这些列已覆盖。

自动增补只接受同一个来源适配器内、相同业务类型、相同已验证全局编码域、相同编码长度及规范化规则的对象，且已有属性共享依据。定义规则的名称列用于提出候选映射；完整的编码到名称函数依赖检查和编码、名称联合匹配用于核验。目标排除列、敏感列、仅供证据的列不进入投影。

核验一致后，修订现有规则的名称属性，经过原执行与发布检查，为同一节点的名称增加本表来源支持。不会创建新对象，也不会把名称加入身份键。不一致或缺少匹配保留 `coverage_shared_label_unresolved`，查询或执行中断保留 `deferred`。

核验只在内存使用源数据，报告只保存列名、状态和计数。当前自动增补限于同源、同名列的精确名称匹配；跨源、不同名称列、别名冲突和新身份域继续由普通发现处理。

## 报告与界面

已拒绝候选显示为处理记录，仅允许用户主动重新调查。运行问题区区分“已拒绝”“分析有缺口”“工作未完成”。关系未决使用 `relation_discovery_unresolved`，执行中断继续使用 `relation_discovery_pending`。未解释列直接显示授权元数据中的列名。

历史实验保留原状态和原文件。本次修改的验收包括拒绝后有效规则仍能发布、相同资料不再自动重问、共享名称增加支持且不增加节点、冲突和超时不会被算作覆盖。代码回归通过不代表真实模型已经完成新一轮全量验收。
