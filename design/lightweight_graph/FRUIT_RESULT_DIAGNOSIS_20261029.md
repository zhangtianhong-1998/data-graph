## 为什么部分完成

实验结束状态为 `PARTIAL`，耗时约 23 分 8 秒、28 次模型调用。API 记录输入 643,179、输出 87,382 tokens，共 730,561；预算账本计 788,951，包含失败调用的保守扣账，二者口径不同。

本次总运行上限 30 分钟，探索阶段使用 75%，约 22.5 分钟，其余时间留给验证与发布。不是模型调用次数到限。

实际原因有：

1. 两个 `entity_key` / `column_group` 候选将整行或多个层级位置作为一个对象，独立粒度审查反驳了它们。宽层级候选独立通过，已发布的 3,966 个节点不属于这两条被拒提案。
2. 1 条宽层级规则贡献了 5 个端点绑定，原调度器据此启动额外 T2 关系发现。它在属性覆盖之前运行，消耗了剩余探索时间。
3. 存在响应截断、提交未完成。时间用尽后，coverage 和身份复核继续遇到相同预算错误；8 次身份复核计数不等于 8 次成功完成的判断。
4. 英文名和主体范围仍未覆盖，因此有已发布图也不能标为完整完成。

没有发现执行器将同一编码重复实例化。存在大量同名异码，有些跨主体，有些在同一主体内。不能只按名称合并，否则会隐藏旧数据本身的不同编码及含义冲突。

“采购预付款占用-梨-批发渠道”在结果里有四个节点：集团合并两个编码、批发中心和深加工厂各一个。集团合并的 `GRP_CASH_9117` 的源父项竟为“滞销果准备-梨”，另一编码 `GRP_CASH_9082` 的父项才是“采购预付款占用-梨”。这些名称与父子关系直接出现在源 Excel；第 2 行就包含该复合名称，后面位置还是相同编码的填充。

因此旧数据既有组合命名问题，也有业务含义可疑的路径。旧 Gold 继承了生成规则，能证明执行器忠实，不能独立证明生成器的业务含义正确。图里没有独立的“梨”或“批发渠道”节点。直接切分连字符会进一步误导，仍需独立编码、角色定义和适用范围。

## 本次代码修改

- **先补已有规则，再探索额外关系。** coverage 提前；已知规则上下文保留完整身份、命名空间、层级、标签及别名映射；修复定制任务说明被通用说明覆盖的问题。模型可提出保留身份与拓扑的属性增补，经过完整执行验证后替换旧修订。
- **避免把一条层级规则的多个位置当成多个对象定义。** 自动关系探索默认要求至少两条独立实体规则。用户明确要求额外关系，或程序发现额外角色证据时，仍可审查单规则关系；既有引用规则仍执行身份级自环检查。
- **预算耗尽只报告一次，不虚增复核次数。** 身份审查提前检查预算；失败后停止后续模型审查，候选仍保留为延期。
- **概念身份与名称分开。** `ConceptComponent.key_column` 使用独立业务编码，原 `column` 提供名称。同名异码保持不同对象；不同类型的相同编码不合并。空编码、一个编码对应冲突标签、同一个上下文绑定不同组合都会阻止发布。
- **概念范围与上下文范围分开。** 组件默认沿用上下文命名空间。缩小概念身份范围必须提供明确文档章节引用；不同主体可复用集团统一概念，但每条来源支持和联合组合仍保留主体权限。
- **评分检查联合关系。** 新增 `evaluate-concepts`，按明确指定的类型、关系映射评分独立概念和主体内的完整联合组合，不把两两边展开成笛卡尔积。修正普通评分器对合法多主体支持的聚合，并识别重复节点 ID。

工作流版本为 `goal_driven_iterations/13`。没有默认切割名称、同名合并或放宽语义门槛。新增编码、范围字段仍通过工具引用白名单、列权限、独立语义审查和完整执行检查。

## 后续修复：预算、范围修订与跨表复用

新版数据的 `config-hierarchy.json`、`config-concepts.json`、`config-full.json` 和生成器保持一致。每个任务独立使用以下上限，不代表三个任务合计的额度：

| 配置 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 总运行时间 | 30 分钟 | 120 分钟 |
| 探索时间 | 22.5 分钟 | 90 分钟 |
| 执行与发布预留 | 7.5 分钟 | 30 分钟 |
| 模型调用 | 80 | 240 |
| 总 tokens | 100 万 | 不限（`max_tokens: null`） |
| 查询总数 | 1,000 | 3,000 |
| 单任务回合 / 探索工具调用 | 12 / 24 | 20 / 48 |
| 单请求超时 | 180 秒 | 300 秒 |

探索最多使用 2,250 次查询，另留 750 次供完整验证。根据后续要求，取消此前设置的 600 万累计 token 上限，主要以 240 次模型调用控制探索额度；token 使用量继续记录。时间、调用或查询额度先到限时仍可能提前结束。单次输出保留 16,384 tokens，响应上限保持 1 MiB；没有假定网关支持更长输出。发现轮数仍为 3，单表关系尝试仍为 2，避免增加预算后反复提交同一种失败解释。

生成器明确保留 `max_tokens: null`，不会因排除空值而恢复默认额度。冻结实验允许累计 tokens 不限，但仍要求有限调用次数；快照与清单保留该选择。新增回归检查使用超过原额度的 token 计数不报错，同时第 241 次调用仍被拒绝。

完成的代码修复：

1. **提交留出反馈时间。** 至少四回合的任务在总回合数内预留最后两回合，只允许本地提交与结束操作。倒数第二回合提交错误时，最后一回合可依据字段诊断修正并结束。20 回合配置因此最多有 18 回合进行来源探索，未增加框架外调用。
2. **范围修订替换旧规则。** coverage 中发现相同对象增加命名空间时，不再按不同规则 ID 并存发布。进入一次明确的 T5 修订，携带旧契约和候选范围列，独立语义审查、全量执行通过后替换同一逻辑规则。仅允许保留对象键与拓扑的范围细化；失败时保留原结果，同时留下 `namespace_scope_missing` 工作项和可读提示。旧规则可执行不再自动消除这个工作项。
3. **依赖关系随身份重建。** 范围修订成功后，重执行已准备的引用关系依赖闭包，再原子发布。若身份键增加使原关系端点列数失配，进入有界关系修订；不能继续发布指向旧身份的边。
4. **明确编码域可以跨表复用。** 普通实体提案支持 `verified_identity_domain`；概念组件可显式填写 `identity_domain`、`identity_evidence` 和 `key_column`。同类型、同域、同范围、同编码才复用。未经声明维持原身份隔离；名称冲突、不同类型同码、部分文档、衍生文档、分析指导或越界文档仍受限制。
5. **传递前表假设。** 同一次发现中，后续表可看到前表提出的编码域、类型定义和来源映射，最多 32 项并明确报告截断。它们仍是待本表验证的假设，不能替代适用文档和独立审查。
6. **修订提示容量。** 默认提示上限由 64 KiB 调整为 128 KiB，使完整旧契约与新增工具 Schema 能共同进入合法修订请求；显式较小配置仍然有效。新版实验原有 256 KiB 配置不变。目录窗口同时按剩余 token 额度扣除输出预留和其他预约，缩小可选表范围，避免请求字节虽合规却在发起前被 token 预算拒绝。
